# SBOM — correcting, re-hashing and signing

This folder holds the project's SPDX 3.0 SBOM and its detached signature:

| File | What it is | Committed? |
|---|---|---|
| `SBOM.spdx30.json` | SPDX 3.0 JSON-LD SBOM (generated by SonarQube, then post-processed) | yes |
| `SBOM.spdx30.json.sig` | Raw Ed25519 detached signature over the JSON bytes | yes |
| `SBOM.spdx30.json.sig.b64` | Same signature, base64 (single line) | yes |
| `sbom-signing-key.pub.pem` | Public key to verify the signature | yes |
| `sbom-signing-key.pem` | **Private** signing key | **never** (git-ignored) |

The scripts that fix up and sign the SBOM live in [`../scripts/`](../scripts/).

## Why the SBOM needs correcting

SonarQube overwrites `SBOM.spdx30.json` on every scan and drops the edits needed to pass
SBOM quality checks. After **every** regeneration you must re-apply them:

1. **`scripts/postprocess_sbom.py`** — on the root `software_Package` (found via
   `SpdxDocument.rootElement`):
   - sets `software_packageUrl`, a `packageUrl` `externalIdentifier` and a `vcs` `externalRef`
     (default PURL `pkg:github/geodis-opensource/dataquality@main`);
   - sets `verifiedUsing` to a SHA-256 over `backend/requirements.txt` + `frontend/requirements.txt`
     (raw bytes, concatenated in that order — equivalent to `cat … | sha256sum`);
   - gives **every dependency package** a `software_packageUrl` and a `packageUrl`
     `externalIdentifier`. SonarQube only emits the PURL as a `buildSystem` `externalRef`
     locator, which quality checks don't count as a package identifier ("Package identifiers
     are missing"). The existing `pkg:pypi/...` locator is reused; if a package has none, one is
     built from its name/version (PEP 503-normalised). Packages with no derivable PURL are
     printed as `WARN:`;
   - sets the root project's `software_copyrightText` to `Copyright 2026` (as in
     `LICENSE`/`NOTICE`; override with `SBOM_PROJECT_COPYRIGHT`);
   - pins the root project's declared and concluded license to `Apache-2.0`;
   - for every dependency, back-fills a `NOASSERTION` declared/concluded license from the other
     side when that side names a real license (it never invents a license).
2. **`scripts/add_sbom_hashes.py`** — adds a `verifiedUsing` SHA-256 to each dependency package,
   taken from the PyPI JSON API (sdist preferred, then a `py3-none-any` wheel, then any wheel).
   Packages it can't resolve are left alone and listed as `FAIL`. Needs internet access to
   `pypi.org`.
3. **`scripts/add_sbom_copyrights.py`** — fills each dependency's `software_copyrightText`
   (SonarQube leaves it empty: "Copyright text is missing"). For the exact package version, it
   reads the license files (`LICENSE*`, `COPYING*`, `NOTICE*`, `AUTHORS*`) shipped in the PyPI
   wheel's `*.dist-info` (falling back to the sdist) and keeps the real `Copyright …` lines.
   Wheels are read with HTTP range requests, so only the license files are downloaded. License
   template placeholders (`Copyright [yyyy] [name of copyright owner]`), license-body clauses and
   the FSF copyright of GPL/LGPL license texts are ignored.
   Many (mostly Apache-2.0) projects ship only the bare license text and keep their copyright in
   source-file headers, so if the license files name no holder the script scans the headers of
   the source files shipped in the wheel. It skips `tests/`, vendored/third-party directories and
   files whose header says the code was taken from another project (so e.g. cffi isn't credited
   to the author of code it embeds). Header statements are ordered by how many files carry them
   (max 10). If still nothing is found, the package gets `NOASSERTION` and is listed in the
   output — nothing is invented. Packages that already have a real statement are skipped.

   As of the last run, these have no copyright statement anywhere in their released
   distributions and stay `NOASSERTION`, which is the correct SPDX value when it can't be
   determined: `trino`, `certifi`, `cffi`, `pydeck`, `opentelemetry-api`, `thrift`. Needs internet access to `pypi.org` and
   `files.pythonhosted.org`; takes about a minute.
4. **Sign** with Ed25519 (`openssl pkeyutl`) and verify.

`scripts/sign-sbom.sh` runs all four steps in order. The Python steps are idempotent, and
Ed25519 is deterministic, so re-running on an already-corrected SBOM gives identical bytes and an
identical signature.

## Steps

### Prerequisites

- Python 3 (`python3` or `python` on `PATH`) — standard library only, no `pip install`.
- OpenSSL 3.x with Ed25519 support (`openssl version`). Git for Windows ships one.
- A bash shell — on Windows use **Git Bash**.
- The real signing key at `SBOM/sbom-signing-key.pem` (get it from the key store / whoever holds
  the `SBOM_SIGNING_KEY_PEM` repo secret), or point `SBOM_SIGNING_KEY` at it.

> ⚠️ If no private key is found, `sign-sbom.sh` **generates a new dev key** and overwrites
> `sbom-signing-key.pub.pem`. The SBOM will still verify locally, but against a different
> identity than the one published. Check `git diff SBOM/sbom-signing-key.pub.pem` before
> committing — it should be empty.

### 1. Regenerate the SBOM (when dependencies changed)

Run the SonarQube scan that produces `SBOM/SBOM.spdx30.json`. Skip this step if you only want to
re-apply the corrections to the existing file.

### 2. Correct, hash and sign

From the repo root, in Git Bash:

```bash
bash scripts/sign-sbom.sh
```

Or with the key somewhere else:

```bash
SBOM_SIGNING_KEY=/path/to/sbom-signing-key.pem bash scripts/sign-sbom.sh
```

Expected output, roughly:

```
>> Post-processing SBOM (PURL + external identifier + manifest hash + licenses)
Injected PURL=pkg:github/geodis-opensource/dataquality@main
Injected sha256=<hash> into <root spdxId>
Package identifiers: N dependency package(s) given a PURL
Normalised licenses: N relationship(s) updated (project=Apache-2.0)
>> Adding per-dependency SHA-256 hashes from PyPI
HASHED/OK: N
FAILED: 0
>> Adding per-dependency copyright text from PyPI license files
COPYRIGHT FOUND: N
NOASSERTION: M
  NOASSERTION: <pkg>==<ver> (no copyright line in wheel: …, sdist: …)
>> Signing .../SBOM/SBOM.spdx30.json with Ed25519
>> Verifying signature
Signature Verified Successfully
>> Done: ...
```

Look at any `FAIL:` lines — those packages have no hash (wrong name/version in the SBOM, package
pulled from PyPI, or no network).

#### Running the steps one by one (optional)

Same order as the script. **Always sign last** — any change to the JSON after signing invalidates
the signature.

```bash
python scripts/postprocess_sbom.py
python scripts/add_sbom_hashes.py
python scripts/add_sbom_copyrights.py
openssl pkey    -in SBOM/sbom-signing-key.pem -pubout | tr -d '\r' > SBOM/sbom-signing-key.pub.pem
openssl pkeyutl -sign -inkey SBOM/sbom-signing-key.pem -rawin \
        -in SBOM/SBOM.spdx30.json -out SBOM/SBOM.spdx30.json.sig
openssl base64  -A -in SBOM/SBOM.spdx30.json.sig -out SBOM/SBOM.spdx30.json.sig.b64
```

### 3. Verify

```bash
openssl pkeyutl -verify -pubin -inkey SBOM/sbom-signing-key.pub.pem -rawin \
        -in SBOM/SBOM.spdx30.json -sigfile SBOM/SBOM.spdx30.json.sig
```

### 4. Keep derived docs in sync

If the dependency list or any license changed, update
[`THIRD-PARTY-NOTICES.md`](../THIRD-PARTY-NOTICES.md) to match the SBOM (see
[`CONTRIBUTING.md`](../CONTRIBUTING.md)).

### 5. Commit

Commit `SBOM.spdx30.json`, `.sig`, `.sig.b64` and (only if you intentionally rotated the key)
`sbom-signing-key.pub.pem`. Never commit `sbom-signing-key.pem`.

## CI

[`.github/workflows/sbom-sign.yml`](../.github/workflows/sbom-sign.yml) runs `scripts/sign-sbom.sh`
on manual dispatch and on pushes touching the SBOM, the `requirements.txt` files or the SBOM
scripts. It reads the private key from the `SBOM_SIGNING_KEY_PEM` repo secret and uploads the
signed files as the `signed-sbom` artifact. Because the output is deterministic, CI's signature
should match the committed one byte for byte.

## Configuration

All optional environment variables:

| Variable | Used by | Default |
|---|---|---|
| `SBOM_FILE` | all | `SBOM/SBOM.spdx30.json` |
| `SBOM_PURL` | `postprocess_sbom.py` | `pkg:github/geodis-opensource/dataquality@main` |
| `SBOM_MANIFESTS` | `postprocess_sbom.py` | `backend/requirements.txt frontend/requirements.txt` (space-separated, repo-relative) |
| `SBOM_PROJECT_LICENSE` | `postprocess_sbom.py` | `Apache-2.0` |
| `SBOM_PROJECT_COPYRIGHT` | `postprocess_sbom.py` | `Copyright 2026` |
| `SBOM_SIGNING_KEY` | `sign-sbom.sh` | `SBOM/sbom-signing-key.pem` |
| `SBOM_PUBLIC_KEY` | `sign-sbom.sh` | `SBOM/sbom-signing-key.pub.pem` |

## Troubleshooting

- **Hash or signature differs between local and CI.** Usually line endings. The scripts write LF,
  but a CRLF checkout of `backend/requirements.txt` / `frontend/requirements.txt` changes the
  manifest hash. `.gitattributes` forces LF for these; after changing it, run
  `git add --renormalize .` and check out the files again.
- **Don't hand-edit the JSON after signing.** Edit, re-run `sign-sbom.sh`, then commit.
- **Don't reformat the JSON** (IDE "format document" etc.). The scripts use a fixed
  `indent=2` and `" : "` separator; any other formatting changes the signed bytes.
